# Trip Planner audit, 2026-08-22

Full, fresh, end-to-end audit of `apps/trip-planner` at master `6a9d1b4` (build 69), done in the
worktree `/home/nikita/projects/shevato-audit-trip-planner` on branch `audit/trip-planner-2026-08-22`.
Audit-first: nothing in the app was changed. Evidence lives in `.audit/` (probe scripts, logs, the five
per-phase findings files) and `.screenshots/audit/` (about 230 screenshots), both gitignored.

Question asked: if a normal person started using Trip Planner heavily today, how confident are we that
the whole application works correctly, consistently, clearly and pleasantly across realistic workflows?

## 1. Overall verdict: Good with notable issues

The core is solid. Every automated layer is green (1,109 unit, 319 function/static, 4,614 root, 512
browser checks), the item lifecycle, money maths, undo/redo, share allowlist, read-only mode, XSS
handling, provider degradation, Places billing discipline and the offline shell all held up under
adversarial probing, and axe scans zero serious/moderate on nine surfaces. A traveller building a
two-city trip, sharing it and using the assistant will get correct totals, correct warnings and no
data loss in the normal paths.

It is "with notable issues" because the audit found one High data-loss path (a share-link tab can
overwrite edits made elsewhere on import), one High correctness hole in a headline feature
(connection warnings silently disappear whenever any note, meal or activity sits between two legs,
which is most real trips), and a cluster of Medium findings where a documented guarantee is not what
the code does: the assistant can un-book a booked reservation, assistant id-matching can never work,
the privacy page states a default the app no longer has, a visa reminder stretches the trip by a
month, the budget is relabelled rather than converted, timed dinners export to calendars as all-day
events, and the day route chain measures a city-change day from the wrong hotel. None of these are
release blockers for a personal planner, all are cheap to fix, and the product-quality review found
the mobile toolbar to be the single largest friction point for a phone user.

## 4. UX problems (current behaviour correct, sorted by impact)

1. **Phone toolbar pushes every view below the fold (MV-C1, High on mobile).** At 390x844 the
   toolbar alone is 393px (Add/Select, an undo/redo row, Shift/Route, Visas/Assistant/?, view tabs,
   search, two or three filter selects); tapping Days or Map leaves the first card/map at y=845 on an
   844px viewport. Cheapest fix: scroll the active view into place on a tab switch on narrow widths;
   better: fold Shift/Route/Visas/? into one "More" button and collapse search+filters behind a
   single "Filter" toggle, put undo/redo beside the view tabs.
2. **Timeline rows on touch carry five always-visible 44px actions (MV-C3).** A hotel row is ~260px
   tall at 390; the Japan example scrolls for ~9 screens. Keep edit/delete inline and fold
   assistant/shift/documents into a `...` like the day header already does.
3. **Days rows on a phone give the title about a third of the card (MV-C2).** Time column + rail +
   tile + two always-visible 32px buttons leave 126px, so hotel names wrap three lines and a long
   flight title breaks mid-word into seven lines with the Ref tag beneath.
4. **Check-out row drawn after a 9:15 departure train on the same day (DM-13).** The assumed
   check-out slot sorts after an early leg, so the day reads "take the train, then check out".
5. **Pre-trip tasks have no home (DM-02/DM-18).** The visa reminder bug is the symptom; `bookBy`
   deadlines are the right primitive and could take a "before the trip" zone in Days view later.
6. **Model-suggested duplicates are not flagged (AS-C1).** A proposal equal to an existing item
   (same title, date, time) renders as an ordinary Add card; the prompt already lists existing items.
7. **Summary chips on a phone are a 1462px horizontal scroller with no affordance (MV-C4).** Three
   chips visible, five off-screen, nothing signals the row scrolls.
8. **Same concept drawn differently across views (MV-C5).** "Google Maps" is a filled pill on the
   Timeline and a quiet text link on Days; Directions has the compass on place rows but not leg rows.
9. **Touch targets under 44px on row-level controls (MV-C7):** status select 34px, Google Maps pill
   28px, Days edit/delete 32px, Directions 30px, night-strip cells 16px, issues "show" 23px.
10. **Smaller wording/affordance items:** visa dialog failure says "close and reopen" while rates
    offer an inline Retry (MV-C6); trip-name field paints a select-style arrow from its datalist
    (MV-C8); pick-one heading derives from the first word of the group id, so a non-compliant reply
    reads "PICK ONE G" (MV-C9); traveller filter default "Everyone" reads as a value next to "All
    types"/"All statuses" (MV-C10); search does not match `costNote` (DM-15); day-card cost prints
    `¥3,800~$25.33` with no separator (DM-16); Cash needed mixes `¥33,100` with `฿45,500.00`
    precision (DM-17); CSV has no `paidBy`/split columns though README calls it the split-the-bill
    sheet (DM-14); a model cost written as "25 USD" is dropped silently (AS-C2); 429 wording is the
    same for per-client and global scopes although `Retry-After` is available (AS-C3); the BYOK block
    never says which provider's key is stored (AS-C4); loading an example into the untouched default
    trip leaves it named "My trip" (lead, T1).

## 5. Reliability / performance concerns

- **Sync edge is no longer rare (AS-B1).** Since the 2026-08-21 meal migration, any remote payload
  written by an older client with a `Dinner:` title (or junk status) triggers a repair write on remote
  apply. Observed signed-out: two `trip-planner:v1` writes during apply, and the other tab's undo
  history reset. No data loss observed; signed in, FINDINGS says the write is swallowed by the echo
  lock. It deserves a re-check once every deployed client carries build 69+, and CR-01 (above) is
  the variant that does lose data.
- **Whole-db sync means `activeTripId` follows across tabs (AS-B2)**: two tabs cannot look at two
  trips, and an open assistant panel re-targets. Accepted consequence of the model; worth one README
  line so it is not reported as a bug.
- **Booking codes, payer, split and payment tags ride into every assistant request (AS-B3)**, all
  three tiers, because the assistant projection is `slimTripForShare`. Privacy says "trip contents",
  which is true; the model cannot use them (they are refused on the way back). Drop them from the
  assistant projection only.
- **Assistant client timeout is 60 s with the composer locked (AS-B4)**; the function's own
  deadline is 45 s, a BYOK hang locks Send for the full minute with only "Sending...".
- **Repair coverage (CR-06/DM-05)** and the **unbounded climate cache (CR-07, ~60 B/entry,
  practically unreachable)** are the two remaining storage-shape risks.
- **Performance is fine at realistic and at extreme sizes**: 120-day / 431-item trip: Days view
  121 cards and 33.7k DOM nodes, view switch 68-76 ms, add item 0.4 s, status change save+render
  68 ms; search/filter has no debounce and costs 30-60 ms per keystroke on the Timeline and 116-158
  ms on Days at 400 items (CR-08, fine on desktop, may stutter on a phone at that size); undo stacks
  hold 50+50 whole-db strings (140 KB db, 19 MB heap, CR-09); the USA example loads in 0.5 s; a
  mis-dated 26,665-night trip caps at 400 days with two named errors and still renders in 1.1 s.
- **Request hygiene is otherwise excellent**: rates fetched exactly once and never refetched across
  10+ re-renders; zero idle polling in every failure mode; Photon one request per debounce; Places
  zero duplicate billed queries across toggles, trip switch and scroll, batch <= 12, concurrency 2,
  free-month park with one toast, client-hour resume; Nominatim spacing never under 1.1 s.

## 6. Accessibility findings

## 8. Recommended improvements and additions (Phase 13, ranked)

Each entry: observed problem, evidence, proposal, benefit, complexity, regression risk, timing, and
whether existing functionality already covers it. The app is feature-saturated (FINDINGS says so and
this audit agrees); the list below is deliberately short and friction-driven.

**P0: address before calling the app polished**

1. Fix the High/Medium defects in section 3 (they are guarantees the README already makes). Nothing
   here is an addition.
2. Mobile toolbar consolidation (MV-C1/C3). Problem: on a phone the chosen view is invisible after
   the tap and each Timeline row is a quarter of the screen. Evidence: `m-map.png`, `m-days-top.png`,
   `tl-m390-rows.png`, probe `content top 845 / vh 844`. Proposal: below 560px fold Shift/Route/
   Visas/? into one "More" button, collapse search+filters behind a "Filter" toggle (the Clear
   filters control already knows when filters are active), put undo/redo beside the view tabs, and
   fold the Timeline row's assistant/shift/documents into a `...` (the day header pattern). Benefit:
   content on screen after every tap, ~3x fewer screens to scroll. Complexity: CSS plus one small
   menu component, no logic. Risk: low (e2e selectors for the folded buttons need updating). Now.
3. Pre-trip tasks via `bookBy` (DM-02). Problem: the visa reminder corrupts every date-derived
   figure. Proposal: make "Add reminder" a Book-by deadline on a to-book note dated on the trip's
   first day (the warnings panel already counts deadlines down), no new concept. Complexity: tiny.
   Risk: none. Now. Existing functionality (booking deadlines) solves it almost entirely.

**P1: strong improvements**

4. Budget currency (DM-03). Store `budgetCurrency`, default to trip currency on read, convert in
   the chip. Small; needs a share/export/repairDb decision for one field. Now-ish.
5. "Already on your plan" badge on assistant proposals (AS-C1). Problem: duplicates render as
   ordinary Add cards. Evidence: as-assist probes. Proposal: compare title+date+time against the
   trip at render. Benefit: prevents double bookings from a repeated ask. Complexity: small, pure.
   Risk: low. Now.
6. Assistant projection trimmed (AS-B3). Drop `confirmation`, `paidBy`, `splitAmounts`, `payment`,
   `bookBy` from what the model receives (keep the share link as is). Privacy win at zero UX cost.
   Small. Now.
7. Import/restore duplicate detection (DM-09/AS-08). Problem: restoring a backup or re-importing a
   share appends copies that then warn against each other. Proposal: carry the original trip id in
   exports and offer Replace / Keep both / Skip on a match (name + span fallback). Medium
   complexity. Risk: medium (import is a data path; needs tests). Later, after the P0s.
8. Failure memo for weather and geocode (PP-01/02/03). A 60 s negative cache for transport failures
   removes the re-fire on every render. Small, pure. Now.
9. Undo affordance on the accepted assistant stub (AS-04/D). Problem: Undo is under the panel.
   Proposal: the stub already knows the added id; a "Remove" link that calls the same undo path.
   Small. Now.

**P2: worthwhile, optional**

10. Light print palette (MV-03) plus a "Print this day" entry in the day menu (discoverability).
11. Days-view in-row status control (CR-C): the Timeline's learned affordance is absent on Days.
12. Consistent Maps/Directions treatment across views (MV-C5); "All travelers" filter label
    (MV-C10); costNote in search (DM-15); separator in the converted cost line (DM-16).
13. Visa dialog inline Retry (MV-C6); provider-specific wording in the BYOK block (AS-C4); scope-
    aware 429 wording using `Retry-After` (AS-C3).
