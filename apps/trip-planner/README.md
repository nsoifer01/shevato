# Trip Planner

**A day-by-day itinerary builder: log flights, stays and activities, watch costs and night coverage add up, get warned about date collisions and uncovered nights, see the whole route on a map, and compare ways to get from A to B.**

## How it works

Everything lives in `localStorage` under the `trip-planner:*` keys and works without an account. Signing in on the site (Firebase Auth, shared header) additionally syncs `trip-planner:v1` and `trip-planner:timefmt` across devices through the shared `sync-system/` (Firestore namespace `tripPlannerApp`); the geocode and venue-coordinate caches stay device-local on purpose. A trip is a named list of items (`flight | stay | transport | local | activity | note`, where `local` is travel within a city), each with dates, optional times (including overnight arrivals like SHV to HND landing +1d), a status (`Booked / To book / Decide later / Cancelled`), and an optional cost (which may be negative to record a refund or credit). Every edit re-renders the summary chips, the night-coverage strip, the warnings panel and the totals instantly.

Most network calls are opt-in and key-free: place lookup via OpenStreetMap Nominatim (cached in `localStorage`, 1 request/second), city suggestions in the place fields via Open-Meteo's geocoding endpoint (a separate provider from Nominatim on purpose: Nominatim's usage policy forbids autocomplete against its public instance), typical weather from Open-Meteo, daily exchange rates from Frankfurter, the visa dataset from GitHub, and map tiles via OpenStreetMap. hotel suggestions on stay items via Photon (OSM data again, but a separate provider from Nominatim for the same reason the city fields use Open-Meteo: Nominatim's usage policy forbids autocomplete, and Photon is built for it). The airport picker makes no network call at all: its table ships with the app under `data/`, and neither does booking import, which reads a confirmation entirely on the device. Leaflet itself is self-hosted under `vendor/leaflet/` (no CDN), loaded on demand the first time the Map view opens. The one keyed, billed call is Google venue ratings. On assistant suggestion cards they appear as a separate star-rating chip; on itinerary items with a Maps place (Timeline and Days views) the score and review count are merged into the item's own Google Maps link, so one element reads `Google Maps · ⭐ 4.7 (1,800)` and opens the resolved place. A travel LEG never gets a rating, on a card or a row: a rating answers "is this worth going to", which is a question about a venue you are choosing between, and nobody is choosing the ride home to a hotel they already booked. A leg that names a real destination gets a `Directions` action instead, opening Google Maps directions from where the leg actually starts in the mode its own distance implies (walking for a short hop, transit otherwise, driving between cities); on Timeline, which has no day chain to ask, the same link is destination-only and lets Maps ask for the starting point. That also spends nothing: a leg makes no Places call at all. Every place a traveller can walk into qualifies, not just the ones the assistant tagged: an item with no `mapsQuery` of its own derives one from its title and location, for stays and activities only (a flight, a between-cities leg, a local hop and a note are not places, so they derive nothing). It stays dormant until the owner configures a Places key (see below); with no key the assistant chips stay empty and invisible while the itinerary link simply reads `Google Maps` with no rating, at zero cost. Offline, the timeline works fully; the map, route lookup, weather and ratings degrade with clear messages. Data sources are credited on the page, with a note that none of them are official sources for entry requirements.

## Features

| Feature | What it does |
| ------- | ------------ |
| Timeline | Chronological board of all items with per-night rates, status pills (quick-change), duplicate/delete, an edit action, and a collapsible stay/day/item hierarchy; filters and search apply here and in Days view. Items with a Maps place show a single Google Maps link that carries the star rating and review count inline (`Google Maps · ⭐ 4.7 (1,800)`, upgrading its href to the resolved place) once ratings are configured, and a plain `Google Maps` link otherwise; the same combined link appears in Days view |
| Bulk actions | "Select items" in the toolbar puts the Timeline into selection mode: every row matching the current filters gets a checkbox, whether it sits at the top level or folded inside a stay, and a bar above the board reads "{n} selected" alongside Select all, a status control and Delete selected. A status change or a delete across the whole selection is one undo step. Parent and child are independent picks, so ticking a stay never reaches inside it and ticking every item inside one never ticks the stay; Select all expands any collapsed group holding a selection so a pick is never invisible; and a stay drawn only because something inside it matches still gets no checkbox of its own. With nothing selected both actions are disabled, and leaving selection mode, switching view or touching any filter clears the selection; a second "Set currency" picker relabels the selected items' costs into another currency without converting the numbers, one undo step |
| Undo / redo | Every data change (add, edit, delete, duplicate, shift, status, import, trip ops) is undoable 50 steps deep: toolbar buttons or Ctrl+Z / Ctrl+Y; history resets when a remote sync merge lands |
| Multiple trips | Create, rename, duplicate and delete trips; per-trip currency (31 ISO codes, the full ECB/Frankfurter set, with the 8 common ones grouped first and any legacy code a trip already uses kept in its own "Saved with this trip" group) switchable from the totals footer picker, with the symbol shown in the Cost column header and as a prefix inside the Cost input |
| Trip essentials | 🆘 Trip essentials in the trip menu keeps the "if something goes wrong" details a buried note item cannot: emergency contact name and phone, insurance provider and policy phone, and free-text medical notes, all optional and all per trip. Blank on every field reads "Nothing saved yet" rather than an empty form, and the menu entry never carries a badge. It rides along in JSON export and Backup all trips and is restored on re-import, and is deliberately kept OUT of CSV, calendar (.ics) and share links: these are the details you least want to hand to someone else along with an itinerary. Deleting a trip takes its essentials with it |
| Search across trips | A 🔎 next to the trip picker searches item titles, places, details and confirmation codes across EVERY saved trip at once, not just the open one, answering "which trip did I put that booking code in". Up to 20 matches list title, date and which trip they belong to, sorted by trip then date, with a "+N more" line past that; picking one switches trips, switches to Timeline, and flashes the row using the same jump-to-row highlight the warnings panel uses. It is hidden entirely on a read-only shared trip, where there is only one trip to search and it is not yours |
| Validation | Blocks bad input (missing title, check-out before check-in, arrival before departure, calendar-impossible or out-of-range dates); negative costs are accepted deliberately as refunds; timezone-aware: a flight may land the same day at an "earlier" local time. A single far-future date can no longer hang the app: day walks stop at a cap and the offending item is named as an error. A double-click on Save (or two rapid Enter presses) adds ONE item, not two: the second submit lands after the first has already saved and closed the dialog, so it is ignored rather than read as a second, independently valid item |
| Warnings | Date collisions (two stays covering the same night), uncovered nights up to the trip's end, past items still "To book"; click-through from the warnings panel to the row. Also flags an impossible connection (a flight/transport/local leg that departs at or before the previous leg arrives) and a tight one (a positive gap under 45 minutes, stated in minutes); legs more than 24 hours apart, a leg with no time, or a hotel night landing between two legs are never treated as a connection. And it nudges when two non-cancelled items share the exact same date and clock time, worded as a double-check rather than a certainty. Every such warning names both items so the jump-to-row link still works. It also looks BEYOND the open trip: if another saved trip covers any of the same calendar days, a line names it and its dates ("Overlaps with another trip: "Lisbon long weekend" (Jun 8 - Jun 15, 2027)"), computed from whichever trip you are looking at so opening either side names the other. The other trip's name is a link that switches to it and leaves your filters alone; trips that merely touch (one ends the day the next begins) raise nothing, and a trip with no dated items can neither raise this nor be named by it |
| Booking deadlines | Any item takes an optional "Book by" date under Status, for the bookings that have to happen before the trip date itself (prices spike, seats sell out). While the item is still "To book" the warnings panel counts it down inside a 7-day window as "book by {date}, 3 days left" (or "today" on the day itself), and calls it out as "booking deadline passed ({date})" once it is behind; both click through to the row like every other warning. Marking the item Booked, Decide later or Cancelled silences it regardless of the stored date, a Book-by date falling after the item's own date is refused inline, and an item carrying no deadline adds no warning and no UI anywhere |
| Night coverage strip | One cell per night, colored booked / decide later / to book / in transit / no stay; hover for details, click to jump. Every jumpable cell is a real control rather than a painted div: it takes keyboard focus with a visible ring, carries a screen-reader label matching its tooltip, and jumps on Enter or Space exactly as it does on a click, with focus following to the rebuilt cell. A cell with nothing to jump to stays unfocusable, so tabbing never stops on a dead square |
| Fill an uncovered night | A "No stay covers ..." warning is the one line in the panel that names nights rather than an item, so it now acts on them: "show" rings exactly those cells in the night-coverage strip for a couple of seconds, and "Add stay" opens the Add-item form already set to Stay with check-in on the first uncovered night and check-out the morning after the last one, read from the same coverage data the warning and the strip are drawn from. Saving it covers the gap and the whole line (control included) disappears; a trip with several holes offers one per line, each filling its own range. Cancelling creates nothing. Absent in a read-only shared view, where nothing can be added |
| Overnight legs | Flights and transport carry arrival date + time; overnight legs show a +1d badge and count as covered (booked) nights |
| Shift dates | Move one item, everything after it, or the whole trip by N days in one action |
| Duplicate a day | Each Days-view card copies every item that starts that day to a target date you pick, in one undoable step. Clones keep a "(copy)" title and a fresh id; start and end dates shift by the same delta, so a three-night stay stays three nights, and a blank or invalid end date is carried across unchanged. The source day is left untouched and anything already on the target date is kept, never overwritten; the button is disabled on a day with nothing starting on it |
| Place picker | The Place field on any item, and both fields in the route dialog, autocomplete against Open-Meteo's geocoding endpoint (keyless, built for typeahead; Nominatim forbids it and stays a one-shot lookup). Rows carry a second line that disambiguates namesakes - "Paris, Île-de-France, France" against "Paris, Texas, United States" - which is the whole reason the old `<datalist>` was not enough. Places already used in the open trip are offered first, tagged "in this trip". Ranking is population-dominant on purpose: "tok" means Tokyo, not the village of Tok, Alaska, though the village is still listed second. Only what the traveller typed is stored (the bare city name, which is also the day-card chip and the weather key), but PICKING a row seeds the geocode cache with that row's country and coordinates, so the map, weather and visa lookups skip Nominatim for it and the visa dialog may name the country outright - a human choosing "Nara, Japan" from a list that also offered Nara, Mali is exactly the certainty the confidence gate exists to look for. Typing without picking behaves as it always did |
| Airport picker | Flight items get From/To airport fields above the title, searching 3,271 IATA airports by city, airport name, code or alias. The table ships with the app (OurAirports, public domain, ~260 KB) rather than coming from an API: every airport API needs a secret key, which a static client-side app cannot hold, and a bundled file also works offline and is precached by the service worker. Aliases matter - Narita's municipality is "Narita", so without them a search for "tokyo" would never find NRT, and "new york" would never find EWR. Picking both writes the title as `City (CODE) to City (CODE)`, the same shape the day cards already parse for a travel day's departure city, so nothing new is stored on the item and a hand-written title is never overwritten. Editing an existing flight re-fills both fields from its title |
| Hotel picker | Stay items search real lodging by name as you type: the Title field is already relabelled "Hotel / stay name" for a stay, and it becomes a combobox there and ONLY there (the other five types keep it a plain free-text title, checked per search because the type switches under an open form). Unlike the airport table this cannot be bundled - OpenStreetMap carries over a million lodging POIs against 3,271 airports in 260 KB - so it is a live lookup against Photon, which is the same OSM data, keyless, CORS-open and built for typeahead (Nominatim forbids autocomplete, Open-Meteo resolves settlements and never POIs). Rows show the town and a HOTEL / HOSTEL / GUEST HOUSE / MOTEL / APARTMENT pill. The city already in the Place field outranks Photon's own order, which is what makes "novotel" with "Bangkok" in the form answer Bangkok rather than Christchurch; a bare chain name with no city is the weak spot, and typing the city too fixes it. Photon's `location_bias_scale`, `zoom` and `bbox` were all tried and rejected - the first two made the bias worse and a bbox hard-filters, returning an EMPTY list for a hotel that is simply not in OSM. Only the bare name is stored, but picking a row seeds the geocode cache with THE HOTEL's coordinates instead of the city centroid every stay used to share, which is the real gain: map pins, leg distances and route legs all sharpen. An empty Place field is filled in from the pick; a filled one is left alone. One Google Places call fires on the pick (never per keystroke) to show the same star-rating chip the assistant cards use, and it stays invisible with no key configured |
| Clear filters | A `✕ Clear filters` control sits in the toolbar whenever any filter or search term is active, and resets the search box, the type, status and traveler filters together. It is hidden when nothing is filtered. Previously the only way out of a filter combination was the link inside the "nothing matches" empty state, which never appeared while a filter still matched something |
| Read-only shared view | Opening a `share=` link renders someone else's itinerary and locks every action that would write to YOUR data. Only export trip (JSON / CSV / .ics), share, and the 12/24-hour toggle stay live in the trip menu; the other ten entries are visibly disabled rather than clickable-but-inert. "Backup all trips" is specifically among them, because in a shared view it produced a file named `trip-planner-backup.json` containing only the stranger's trip, which would have looked like total data loss on restore. The trip picker, the status pickers and the currency picker are disabled too, the cross-trip search is hidden entirely, and the `n` keyboard shortcut no longer opens the Add-item dialog |
| Read a booking PDF | `📄 Read a booking PDF` in the trip menu takes a flight or hotel confirmation - a PDF, or pasted text - and offers the items it found as ordinary proposal cards. Deterministic, not AI: airport codes resolve against the bundled table, and dates, times, booking reference and price are read by pattern. **The file is never uploaded and never stored**; it is read into memory, turned into text, and dropped, so nothing lands in the documents pocket. Every reading shows the LINE it came from and a confidence, because a wrong read has to be visible rather than merely plausible in a form field. Accepting one goes through the same validation, undo and save path as an assistant suggestion. Its one extra privilege is transcription provenance: a confirmation code and a `booked` status survive from a document (they were copied, not invented) where they are stripped from a model, and a transcribed price counts as real cost rather than an estimate. Dates are the delicate part: `08/12/2027` is read month-first by default, but a decisive date elsewhere on the page overrides that, and failing one, the reading that produces a possible trip wins - a confirmation whose dates imply a 31-day flight is being read the wrong way round. European document formats are read too: comma-decimal money ("EUR 148,00", "1.234,56 EUR") parses as the price it is rather than a hundredfold of it, a dotted date ("12.08.2027") or a price line is never mistaken for a clock time (a mistake that used to fabricate an overnight leg), and a "+1 800..." customer-service phone number no longer reads as a next-day arrival marker. Booking references require the letter inside the code itself (so a date or an all-digit number next to the label is never a PNR), and uppercase day/month abbreviations that double as real airport codes (SAT, SUN, AUG) are ignored for bare-code route sniffing - the parenthesised "(SAT)" form still matches, so a genuine San Antonio flight keeps its route. Whichever settled it is stated on screen (and the day-order note only appears when an all-numeric date is actually on the page). A connection printed as repeated Depart/Arrive blocks (the airline "My Trips" layout) reads EVERY leg as its own flight - route, date, both times, flight number and seat per leg - instead of collapsing six flights into one; leg dates printed without a year ("Tue, Dec 29") resolve against the document's own full dates, exactly when one names the same day, otherwise by the only year that fits the document's dated span, and a date neither rule settles is left blank with a warning rather than guessed. An arrival date printed on the page always beats the wrapped-clock overnight inference, so an eastbound date-line crossing that lands earlier than it took off stays same-day. PDF text comes from pdf.js, vendored under `vendor/pdfjs/` like Leaflet and loaded only when a PDF is actually chosen (1.7 MB, deliberately NOT precached: the runtime cache picks it up after first use). It parses in-process rather than in a worker - a confirmation is one or two pages and takes about 10 ms, and skipping the worker removes a class of environment-dependent failure. A forty-line built-in reader remains as an offline fallback. A PDF that opens fine but contains no actual text (a scan, or a printer-driver "print to PDF" that draws every letter as shapes) is diagnosed as a picture of text: the dialog explains that no app can copy text out of such a file and points to the source email or booking page instead, rather than sending anyone off to try select-and-copy in a viewer where it cannot work |
| Route map | Numbered stops in visit order connected by a dashed route line (Leaflet + OSM, dark-mode tiles) |
| How to get there | Between consecutive stays in different places: distance (km/mi), compass heading, international-border flag, per-mode duration estimates, and pre-filled links to Google transit/driving, Google Flights and Rome2Rio |
| Import / export | JSON per trip, full backup of all trips, CSV export (includes per-item currency + converted columns, plus confirmation, travelers, bookBy and paymentMethod columns appended in that order so older spreadsheets keep their column order, the payment column carrying the picker's own wording rather than the stored token); import accepts trip files or full backups and re-normalizes traveler names against the trip roster. Attached documents are never included in exports |
| Calendar export | Export trip (.ics) in the trip menu: stays as all-day ranges, flights/transport as floating local-time events (overnight arrivals land on the right day), cancelled items excluded; imports into Google/Apple Calendar. A confirmation code rides along as a `Ref:` line in the event description, since the calendar entry is what a traveler opens at the gate, and a Book-by date and a payment method join it as `Book by:` (spelled out, not ISO) and `Payment:` lines whenever they are set |
| Calendar import | The Read a booking PDF dialog also reads .ics calendar files (file or paste, indented/quoted pastes included): each event becomes an approve-before-adding proposal card; recurring events import their first occurrence and say so |
| Route export (GPX) | Export route (GPX) in the trip menu writes one waypoint per located stop in visit order, for offline map apps; greyed out with an explanatory tooltip until at least two places have been located |
| Copy a day | A clipboard button on each Days-view card copies that day as message-ready text: emoji date header, timed rows with type icons, untimed rows bulleted, the night's stay last; the button flashes a checkmark and covered-but-empty nights copy their "Staying at" line |
| Spend over time | A weekly-bars block beside Cost by type shows WHEN the booked money goes, on trips spanning two-plus calendar weeks |
| Pace note | Four or more stays averaging under two nights each adds an informational "Fast pace" line to the issues panel, counted as a note, never a warning |
| Mark booked from a warning | Booking-deadline warnings that name a single to-book item carry a one-click "Mark booked" beside the jump link |
| Update prompt | A tab left open across a redeploy gets a "A new version of Trip Planner is ready." toast with Refresh and Dismiss, instead of silently running stale code |
| Installable PWA | manifest.webmanifest + sw.js (network-first: online loads always get the newest code; caches are an offline fallback only); timeline works offline after one visit, external APIs are never intercepted |
| Days view | Third view tab: one card per trip day with check-ins, check-outs, timed events, a "Nothing planned, staying at {hotel}" line on days covered only by a stay, and honest "No plans yet" days with no bed; today highlighted; print-friendly (printing in Days view outputs just the cards). Every row is the same shape - type tile, then the title with its city riding inline right after it ("Lunch: Konoba Hvaranin 📍 Split", one line instead of two), then price + Google Maps, then edit and delete - and the row asks its own CARD width (a container query, not the viewport) whether the price and Maps sit beside the title or wrap to their own line, so every card on a page wraps the same way. On the rail, a booking's status dot is a filled disc while an activity's (sights, meals, drinks - plans, not bookings) is a ring in the same status colour, so a day of to-book lunches does not read as one amber wall next to the flights that actually need chasing. Cancelled rows carry a `Cancelled` badge and dim the two controls that are no longer actionable, keeping edit and delete at full strength |
| Order a day by hand | Rows that TIE (same date and the same clock time, "no time set" included) get a drag handle next to edit and delete, and dragging one above or below another stores that order. Only a tie is offered one: a row with a time of its own, a row that is the only one at its time, and both ends of a stay (drawn at assumed check-in / check-out positions rather than a typed time) carry no handle at all, and a drag that wanders onto another day or onto a differently-timed row moves nothing. The handle is a real button: Arrow Up / Arrow Down move the row a step at a time and focus follows it, so the feature is not mouse-only, and it is built on pointer events so the same drag works with a finger. One drag is one undo step for the whole day, the order rides through JSON export/import and share links, and it is what the Timeline reads too. A trip nobody has reordered stores nothing and renders exactly as it did before; handles are also withheld while a filter is on, since half a group cannot be put in an order you can see |
| Budget | Optional per-trip budget in the trip dialog, entered as a pair of boxes ("from" and "to") that hold one value: leave BOTH blank for no budget at all, which is a first-class answer and says so in the dialog (no chip, no bar, no budget wording anywhere), fill "to" on its own for a plain ceiling, or fill both for a range like $3,000.00-$5,000.00. A lower figure above the upper one, a lower figure with no upper one, and a negative at either end are all refused inline with the same invalid-field pattern the rest of the dialog uses. The ceiling is what is STORED as the budget, so the verdict, the bar and every old single-number budget are unchanged and nothing migrates; the range only adds the lower end to what the chip prints. Summary chip shows confirmed-vs-budget and turns amber when exceeded. It never reads green over a total that silently excluded unconvertible money, and it reports a net refund honestly rather than painting green over a negative. The three summary chips that state a part-of-whole ratio in text (Progress, Nights booked, Budget) each carry a thin proportional bar under the value, reusing the same bar the Cost-by-type rows use, so the ratio reads at a glance instead of needing two figures and a division. The bar never introduces a number the chip's own text does not already state, never renders past 100% when spend exceeds budget, and renders at zero rather than negative on a refund; the chips carrying no ratio are untouched |
| Cost per traveler | Name two or more travelers (comma-separated, up to 6) in the trip dialog and each item's Booking section gains a "Who's this for" control. An item left as Everyone splits evenly across all travelers; pick some names to split it only among them. A "Cost per traveler" block under the totals bar shows each person's converted total, and a traveler owed an amount that could not be converted is flagged amber the same way the Confirmed total is, never silently under-counted. A trip that names no second traveler shows none of this and computes exactly as before |
| Uneven splits | Real shared costs are rarely even, so with two or more specific people picked on a costed item a "Split evenly / Split by amount" toggle takes exact per-person figures instead of an automatic divide. Switching to it prefills the even split and distributes the odd cent (a $100 item across three opens as 33.34/33.33/33.33), so the default always adds up. Amounts that do not sum to the item's cost, checked to the cent, block the save with "Split amounts must add up to {cost}" rather than storing a total that lies. Cost per traveler and Settle up both spend the real figures, so a $70/$30 item settles as $70/$30. Changing who the split is for keeps the numbers already typed and only fills one in for anyone newly added; dropping below two people discards them and reverts to an even split |
| Settle up | With two or more named travelers, each item's "Who's this for" section also asks who actually paid ("Paid by", defaulting to a blank "Not tracked"). A "Settle up" block under the per-traveler totals nets every Booked, convertible, payer-tagged cost down to the fewest possible payments and states them as "{debtor} owes {creditor} {amount}", so two people who each covered different bookings see one line, not two. Amounts are rounded to cents before pairing, so a stray sub-cent line can never appear. Nothing tagged yet reads "Add \"Paid by\" to a cost to see who owes whom" rather than a row of misleading zeroes, and everything squaring up reads "All settled up" in green with a ✅, visually distinct from that gray not-set-up-yet placeholder so the one piece of good news the card delivers does not read like a prompt to go do something. A payer is re-spelled or dropped when the roster is edited, so a name that left the trip never lingers |
| Cost by type | A "Cost by type" block under the totals bar breaks the trip's Booked, costed items down per type (Flight, Stay, Transport, Local travel, Activity, Note), biggest first, in the display currency. A type with nothing booked and costed gets no row at all rather than a $0.00 placeholder, and a row holding money that could not be converted is flagged amber with "+ N not converted", the same honesty rule the Confirmed total follows. Each row carries a thin proportional bar sized against the largest row, so the line item eating the budget is obvious without comparing figures; an amber unconverted row keeps its normal bar color, leaving the honesty cue on the text alone. It is gated on cost data alone, so it shows on a solo trip too |
| Cash needed | Each item's Booking section takes an optional payment method (Not tracked, Cash, Card, Prepaid / already paid). Tag anything as Cash and a "Cash needed" block under the totals answers how much cash to carry per currency, in the currency actually entered and never converted, so a Japan-plus-Thailand trip reads its yen and its baht as separate lines. One row per currency, sorted by code, and a currency holding nothing gets no row rather than a $0.00 placeholder; a refund nets into its currency and is not hidden. Cancelling an item or untagging it drops the amount on the next render. It is gated on cash tags alone, so it shows on a solo trip too. This block and the Cost per traveler, Settle up and Cost by type blocks now read as one iconed group set apart from the totals bar, rather than a stack of identical cards |
| Filter by traveler | With two or more named travelers the toolbar gains a third filter next to type and status. Picking a name narrows Timeline and Days view to that person's agenda: their own items plus everything left as Everyone. It ANDs with the type, status and search filters, and it changes only which rows are drawn, never what is computed, so the night-coverage strip, the warnings panel and the totals bar all keep reading for the whole trip. Clearing filters resets it, and a name the next trip's roster lacks is dropped rather than silently hiding rows |
| Item count | An "Items" chip in the summary bar counts the trip's active itinerary items ("12 items", "1 item"). Cancelled items are out, since cancelling reads as removal from the plan, and restoring one puts it straight back. It is a whole-trip figure: filters and search never change it, and it shows on a read-only shared trip too, being purely informational. Derived from `tripStats` on every render, nothing stored |
| Up next | A live chip at the front of the summary row answers "what now" mid-trip. Items carrying both a date and a real clock time qualify (a stay's assumed check-in time is not a fact, so stays never do); inside a flight, transport or local leg it reads `Now: {title}`, otherwise it counts down the soonest item within 36 hours as `Up next: {title} in 2h`. Past that window, or with nothing left to time, it does not render at all. It repaints itself every 30 seconds, and clicking it jumps to that row on the Timeline |
| Packing list | 🎒 Packing list in the trip menu keeps a per-trip checklist with a "{checked} of {total} packed" counter. It is seeded once, on first open, from what the trip actually contains: universal basics always, a boarding-pass row only when the trip has a flight, and a warm-layer row only when a leg runs overnight. After that it is yours: it is never reseeded, adds and deletes and checks are each one undo step, and a list you empty completely stays empty instead of springing back. The seeding itself is deliberately NOT an undo step - the app laying down its own defaults is housekeeping, not an edit the traveller made, so merely opening the dialog never arms Undo (and can never be undone out from under the list you are looking at). It rides along with the trip through save and sync, and is deliberately kept out of share links |
| Per-traveler packing | On a trip naming two or more travelers each packing row can say who it is for, using the item form's own checkbox-per-traveler control on the add form; nothing ticked (and everybody ticked) means Everyone, which is what every row stored before this existed. The dialog gains a "Show" filter listing each traveler with their own tally, and picking one narrows the list to their rows plus every Everyone row, with the "{checked} of {total} packed" counter reading the filtered set rather than the trip. Rows are keyed by id, so checking one person's row never touches another's identical-text row. Below two travelers none of it is built at all: no filter, no picker, no tags, the list exactly as it was. | Duplicate as template | Alongside Duplicate trip, "🧩 Duplicate as template" copies the SHAPE of a trip and drops the booking: every item keeps its title, type, place, times, details and relative day spacing, and every item comes back as "To book" with cost, estimate, cost note, confirmation, book-by date, payment tag, paid-by, who-it-is-for and hand-entered split cleared. Minutes are spelled out ("20 min", never "20m") because the abbreviation reads as metres beside a distance. Accepting a card changes nothing about the number: it becomes an itinerary item and the same origin rule finds it, which is why the figure before the add equals the figure after it. With two or more located ACTIVITY recommendations for a day (a travel leg is not a stop on a walk), a footer line under them reads `Shortest route: Hotel > B > A > C · ~5.4 km / 3.4 mi total` and each named card gets a numbered order pill (the number is the signal, the accent fill is the redundant cue). The order is exact up to 8 stops and nearest-neighbour above that, always starting from that day's own origin, so a reply planning two days routes each from its own bed. Flipping the pick inside a set recomputes the order, the pills and the total; accepting or dismissing a card recomputes both, and the footer disappears below two located recommendations |
| Typical weather | Day cards show a typical temperature range for {place} that month, averaged over the last 5 years of Open-Meteo history (cached per place+month), with a visible caveat that it is historical climate, not a forecast |
| Near-term forecast | A trip day inside Open-Meteo's keyless 16-day forecast horizon shows the actual forecast for that day instead, on the same chip, tagged `Forecast` and carrying its own tooltip ("Forecast 24-34°C in Tokyo, overcast, 69% chance of rain, 70% average humidity. The forecast for this day, not a typical-for-the-month average."). The chip itself carries a condition icon (clear, partly cloudy, overcast, fog, rain, snow or thunder, mapped from the day's WMO `weather_code` and derived from the rain chance only when no code was served), the temperature range, the chance of rain whenever it is above 0% and the average humidity whenever the API supplies it. The two percentages take different markers, an umbrella for rain and a droplet for humidity, and each has its own tooltip, because a chip this small cannot afford to state which figure is which twice. It is a second source, not a replacement: the historical lookup still runs for those days, so a failed or timed-out (12s) forecast falls silently back to the climate chip rather than leaving a blank or a spinner, and a day past the horizon is untouched. Offline the chip is the climate one, cached forecast or not: a forecast that cannot be refreshed or checked is not one worth labelling as such. Cached in its own `trip-planner:forecast:v2` store keyed by place+DATE (the climate cache is place+month and never expires; a forecast expires after 3 hours and stale entries are dropped at load, never served; v1 entries predate the icon and the humidity and are retired outright rather than painted half-empty), and fetched one request per place covering its whole near-term run rather than one per day, with the code and the humidity riding along as daily variables in that same request. The Open-Meteo credit under the grid covers both sources, and gains a sentence about the tagged chips only once one has actually been painted. A chip this full no longer fits beside four action buttons, so a card carrying it restructures its header around one hierarchy: the day badge anchors the left edge spanning the full height, the date and the chip form a single left-aligned block (same left edge, chip snug under the date rather than a stray row beneath it), and the action cluster sits vertically centered opposite the block (on a phone it rides beside the date and the chip runs under it, keeping the city name on screen). The header's action buttons also run a size smaller than the in-row ones so the cluster reads lighter than the content, and above tablet width every day-card header gathers them into a single quiet segmented pill (the tablet range keeps its thumb-size buttons and the phone its 44px targets). On a desktop card wide enough to hold it (a container query on the card, 545px+, since the auto-fill grid hands out different card widths at the same viewport) the whole forecast header collapses onto ONE line at exactly the height of a forecast-less header, with the chip a step tighter and the tag in mixed case, so adjacent cards never disagree about how tall a header is; narrower cards keep the stacked block. Cards without a forecast keep the single row they always had |

| AI assistant | 🤖 A picker builds the request (slot types and counts, style, wake/return times, repeats, budget, free text) instead of the traveller typing prose, and the same request feeds all three tiers. The budget row is optional and multi-select: each tier ($ to $$$$) toggles on its own, so one tier reads as itself, an unbroken run as a range ("$$-$$$" in the summary, "mid-range or upscale" in the request), and no tiers at all is a first-class answer - the request then says nothing about money. Replies come back as separate timed items rather than one blob, with alternatives per slot the traveller picks between before anything is added: the GUIDED picker asks for exactly 3 candidates per meal and drinks slot and a choice of 2 per other activity, which is the contract its bounded controls promise. Free-form chat does not inherit that and carries no option limit of its own: ask it for 5, for 10, or for "more", and it gives that many, defaulting to the same 3-and-2 only when no number is named. The one constraint it is told about is a reply-SIZE one rather than a count (the fenced JSON sits at the end of an answer, so an overrun loses the cards instead of shortening them), and it is told to handle that by covering what fits, saying how much that was and offering to continue, never by refusing or silently trimming. The two modes differ by one paragraph of the prompt, and the mode rides on each REQUEST rather than on the conversation, so a follow-up typed into the composer is free-form even in a thread the picker started. Transport, local hops, stays and notes stay single proposals in both; a candidate set is headed by the slot itself ("Lunch · 1:00 PM"), never by its internal group id. Edits arrive as accept/reject proposal cards (never auto-applied, never marked Booked or Cancelled, an update never un-books a real reservation, and every accept flows through undo). Three tiers chosen from a privacy-labelled picker: (1) copy/paste a ready-made package into any AI and paste its reply back, no key and nothing sent; (2) bring your own OpenAI or Gemini key, stored only in this browser, calling the provider directly; (3) the site's free shared assistant (Google Gemini, rate-limited per day). The assistant refuses to state visa, passport, vaccination or customs rules and points at the destination government instead. Replies render Markdown; chat history is kept per trip in `localStorage` (capped at 40 messages) and can be cleared - and because a thread lives outside the trip db, undo can never bring one back, so "Clear chat" asks first through the same confirm dialog every other destructive action uses, counting the messages at stake and saying the trip itself is untouched; an already-empty thread clears with no question, since there is nothing to lose; a suggestion always carries a distance chip naming its origin, and a VENUE suggestion also carries a Google Maps verify link plus, when an owner Places key is configured, a Google star rating. A travel leg carries neither: it gets a Directions action instead and never a rating, because it is not a place anyone is choosing between. The model is told that the app measures distance itself and where the traveller is based that day, so it neither claims it cannot give distances ("no live GPS or real-time traffic" is true of a model and false of this product) nor invents a walking time or a fare in its prose |

## Site assistant setup (owner)

Tier 3 (the free shared assistant) is served by the Netlify function
`netlify/functions/tp-assist.mjs`, which proxies Google Gemini behind per-client
and global daily rate limits. Env vars are not injected into functions on this
site, so the shared key lives in a Blob, written once out-of-band:

```
# 1. Get a free Gemini API key at https://aistudio.google.com/apikey
# 2. Point the CLI at the project that serves shevato.com (blob stores are
#    per-project, so writing this while linked elsewhere silently does nothing):
netlify status
# 3. Store it (the key never travels over HTTP; it is set via the CLI):
netlify blobs:set trip-planner-assist config '{"geminiKey":"<key>"}'
# Disable the shared assistant again:
netlify blobs:set trip-planner-assist config '{}'
```

With no key set the endpoint returns `503 not_configured` and the UI tells the
traveller to use Tier 1 or bring their own key. Tiers 1 and 2 need no setup.

Two failure modes look alike from the browser but are not: `503 not_configured`
means the key is missing from *this* project's store, while `502 upstream` means
the key was found and Gemini itself rejected the call (most often a retired
`GEMINI_MODEL` pin, see the note in `tp-assist.mjs`). A `429` means a quota was
hit, either this function's own daily limits or Google's. The function logs the
upstream status and body; the key is never logged.

**Google's free tier is the real ceiling, not our limiter.** Measured
2026-07-19 on a free key: `gemini-3.5-flash` allows 5 requests/minute and
250K tokens/minute, and the API refuses further calls once a
`generate_content_free_tier_requests` allowance of about 20 (apparently daily)
is spent. This function's own caps (10/client/hour, 30/client/day, 400/day
global, in `lib/tp-assist-quota.mjs`) are far above that, so on the free tier
travellers hit Google's wall first and see "at capacity". Check the real numbers
at https://aistudio.google.com/rate-limit; enabling billing on the Google Cloud
project raises the limits and costs fractions of a cent per turn.

## Tests

Three layers, lowest appropriate layer wins:

```
npm run test:trip-planner        # unit/domain: node --test against trip-logic.js
npm run test:trip-planner:e2e    # browser E2E: headless Chromium over the real app
npm run test:trip-planner:e2e:headed   # same, in a visible browser for debugging
```

Pure-logic tests via `node --test` against `js/trip-logic.js` (dual-exposed as
`window.TripLogic` and a CommonJS module). No installs, no config. The Tier 3
function's quota math and request guards have their own suite (run by the root
`npm test`, or on their own with `npm run test:tp-assist-quota`).

The E2E suites under `e2e/` run on the repo's zero-dependency CDP harness
(`tests/browser/`, the same one `npm run test:browser` uses, which also runs
them in CI on every pull request). The runner starts its own static server
(port 8099) and headless Chromium, runs the suites, and tears both down;
nothing needs to be running beforehand. Chromium or Chrome on `PATH` (or
`CHROME_BIN`) is the only requirement. They cover the workflows a DOM-free
test cannot: bootstrap, create-and-reload persistence, the item lifecycle,
undo/redo wiring, double-submit guards, multi-trip separation, stale-dialog
guards, two-tab reconciliation, read-only shares, import-as-mine, XSS
rendering, filters, warnings navigation, dialog mechanics, keyboard
shortcuts, Days view, responsive smoke at 1280/390/360, a ~340-item trip,
an offline reload against the service worker's precache, and the assistant's
suggestion cards: distance before the add agreeing with the itinerary after
it, origin selection across arrival / check-in / previous-stop / earlier
suggestion, the visible walk-or-taxi estimate, a five-candidate slot rendering
five, travel-leg semantics (no rating, Directions with the right origin and
mode, its own cost kept), the no-coordinates and same-centroid cases, mobile
chip wrapping at 390px, and guided vs free-form mode read off the actual
request body. External
providers (Photon, Open-Meteo, Nominatim, Frankfurter, Google, Firebase) are
blocked per page by default so runs are deterministic; a failing check drops
a screenshot into `.screenshots/e2e-trip-planner/` (gitignored). See
FINDINGS "Browser E2E suite" for the architecture and the traps.
