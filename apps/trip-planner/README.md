# Trip Planner

**A day-by-day itinerary builder: log flights, stays and activities, watch costs and night coverage add up, get warned about date collisions and uncovered nights, see the whole route on a map, and compare ways to get from A to B.**

## How it works

Everything lives in `localStorage` under the `trip-planner:*` keys and works without an account. Signing in on the site (Firebase Auth, shared header) additionally syncs `trip-planner:v1` and `trip-planner:timefmt` across devices through the shared `sync-system/` (Firestore namespace `tripPlannerApp`); the geocode cache stays device-local on purpose. A trip is a named list of items (`flight | stay | transport | local | activity | note`, where `local` is travel within a city), each with dates, optional times (including overnight arrivals like SHV to HND landing +1d), a status (`Booked / To book / Decide later / Cancelled`), and an optional cost (which may be negative to record a refund or credit). Every edit re-renders the summary chips, the night-coverage strip, the warnings panel and the totals instantly.

Most network calls are opt-in and key-free: place lookup via OpenStreetMap Nominatim (cached in `localStorage`, 1 request/second), city suggestions in the place fields via Open-Meteo's geocoding endpoint (a separate provider from Nominatim on purpose: Nominatim's usage policy forbids autocomplete against its public instance), typical weather from Open-Meteo, daily exchange rates from Frankfurter, the visa dataset from GitHub, and map tiles via OpenStreetMap. The airport picker makes no network call at all: its table ships with the app under `data/`, and neither does booking import, which reads a confirmation entirely on the device. Leaflet itself is self-hosted under `vendor/leaflet/` (no CDN), loaded on demand the first time the Map view opens. The one keyed, billed call is Google venue ratings. On assistant suggestion cards they appear as a separate star-rating chip; on itinerary items with a Maps place (Timeline and Days views) the score and review count are merged into the item's own Google Maps link, so one element reads `Google Maps · ⭐ 4.7 (1,800)` and opens the resolved place. Every place a traveller can walk into qualifies, not just the ones the assistant tagged: an item with no `mapsQuery` of its own derives one from its title and location, for stays and activities only (a flight, a between-cities leg, a local hop and a note are not places, so they derive nothing). It stays dormant until the owner configures a Places key (see below); with no key the assistant chips stay empty and invisible while the itinerary link simply reads `Google Maps` with no rating, at zero cost. Offline, the timeline works fully; the map, route lookup, weather and ratings degrade with clear messages. Data sources are credited on the page, with a note that none of them are official sources for entry requirements.

## Features

| Feature | What it does |
| ------- | ------------ |
| Timeline | Chronological board of all items with per-night rates, status pills (quick-change), duplicate/delete, an edit action, and a collapsible stay/day/item hierarchy; filters and search apply here and in Days view. Items with a Maps place show a single Google Maps link that carries the star rating and review count inline (`Google Maps · ⭐ 4.7 (1,800)`, upgrading its href to the resolved place) once ratings are configured, and a plain `Google Maps` link otherwise; the same combined link appears in Days view |
| Bulk actions | "Select items" in the toolbar puts the Timeline into selection mode: every row matching the current filters gets a checkbox, whether it sits at the top level or folded inside a stay, and a bar above the board reads "{n} selected" alongside Select all, a status control and Delete selected. A status change or a delete across the whole selection is one undo step. Parent and child are independent picks, so ticking a stay never reaches inside it and ticking every item inside one never ticks the stay; Select all expands any collapsed group holding a selection so a pick is never invisible; and a stay drawn only because something inside it matches still gets no checkbox of its own. With nothing selected both actions are disabled, and leaving selection mode, switching view or touching any filter clears the selection |
| Undo / redo | Every data change (add, edit, delete, duplicate, shift, status, import, trip ops) is undoable 50 steps deep: toolbar buttons or Ctrl+Z / Ctrl+Y; history resets when a remote sync merge lands |
| Multiple trips | Create, rename, duplicate and delete trips; per-trip currency (USD, EUR, GBP, ILS, JPY, THB, ...) switchable from the totals footer picker, with the symbol shown in the Cost column header and as a prefix inside the Cost input |
| Trip essentials | 🆘 Trip essentials in the trip menu keeps the "if something goes wrong" details a buried note item cannot: emergency contact name and phone, insurance provider and policy phone, and free-text medical notes, all optional and all per trip. Blank on every field reads "Nothing saved yet" rather than an empty form, and the menu entry never carries a badge. It rides along in JSON export and Backup all trips and is restored on re-import, and is deliberately kept OUT of CSV, calendar (.ics) and share links: these are the details you least want to hand to someone else along with an itinerary. Deleting a trip takes its essentials with it |
| Search across trips | A 🔎 next to the trip picker searches item titles, places, details and confirmation codes across EVERY saved trip at once, not just the open one, answering "which trip did I put that booking code in". Up to 20 matches list title, date and which trip they belong to, sorted by trip then date, with a "+N more" line past that; picking one switches trips, switches to Timeline, and flashes the row using the same jump-to-row highlight the warnings panel uses. It is hidden entirely on a read-only shared trip, where there is only one trip to search and it is not yours |
| Validation | Blocks bad input (missing title, check-out before check-in, arrival before departure, calendar-impossible or out-of-range dates); negative costs are accepted deliberately as refunds; timezone-aware: a flight may land the same day at an "earlier" local time. A single far-future date can no longer hang the app: day walks stop at a cap and the offending item is named as an error |
| Warnings | Date collisions (two stays covering the same night), uncovered nights up to the trip's end, past items still "To book"; click-through from the warnings panel to the row. Also flags an impossible connection (a flight/transport/local leg that departs at or before the previous leg arrives) and a tight one (a positive gap under 45 minutes, stated in minutes); legs more than 24 hours apart, a leg with no time, or a hotel night landing between two legs are never treated as a connection. And it nudges when two non-cancelled items share the exact same date and clock time, worded as a double-check rather than a certainty. Every such warning names both items so the jump-to-row link still works. It also looks BEYOND the open trip: if another saved trip covers any of the same calendar days, a line names it and its dates ("Overlaps with another trip: "Lisbon long weekend" (Jun 8 - Jun 15, 2027)"), computed from whichever trip you are looking at so opening either side names the other. The other trip's name is a link that switches to it and leaves your filters alone; trips that merely touch (one ends the day the next begins) raise nothing, and a trip with no dated items can neither raise this nor be named by it |
| Booking deadlines | Any item takes an optional "Book by" date under Status, for the bookings that have to happen before the trip date itself (prices spike, seats sell out). While the item is still "To book" the warnings panel counts it down inside a 7-day window as "book by {date}, 3 days left" (or "today" on the day itself), and calls it out as "booking deadline passed ({date})" once it is behind; both click through to the row like every other warning. Marking the item Booked, Decide later or Cancelled silences it regardless of the stored date, a Book-by date falling after the item's own date is refused inline, and an item carrying no deadline adds no warning and no UI anywhere |
| Night coverage strip | One cell per night, colored booked / decide later / to book / in transit / no stay; hover for details, click to jump. Every jumpable cell is a real control rather than a painted div: it takes keyboard focus with a visible ring, carries a screen-reader label matching its tooltip, and jumps on Enter or Space exactly as it does on a click, with focus following to the rebuilt cell. A cell with nothing to jump to stays unfocusable, so tabbing never stops on a dead square |
| Overnight legs | Flights and transport carry arrival date + time; overnight legs show a +1d badge and count as covered (booked) nights |
| Shift dates | Move one item, everything after it, or the whole trip by N days in one action |
| Duplicate a day | Each Days-view card copies every item that starts that day to a target date you pick, in one undoable step. Clones keep a "(copy)" title and a fresh id; start and end dates shift by the same delta, so a three-night stay stays three nights, and a blank or invalid end date is carried across unchanged. The source day is left untouched and anything already on the target date is kept, never overwritten; the button is disabled on a day with nothing starting on it |
| Place picker | The Place field on any item, and both fields in the route dialog, autocomplete against Open-Meteo's geocoding endpoint (keyless, built for typeahead; Nominatim forbids it and stays a one-shot lookup). Rows carry a second line that disambiguates namesakes - "Paris, Île-de-France, France" against "Paris, Texas, United States" - which is the whole reason the old `<datalist>` was not enough. Places already used in the open trip are offered first, tagged "in this trip". Ranking is population-dominant on purpose: "tok" means Tokyo, not the village of Tok, Alaska, though the village is still listed second. Only what the traveller typed is stored (the bare city name, which is also the day-card chip and the weather key), but PICKING a row seeds the geocode cache with that row's country and coordinates, so the map, weather and visa lookups skip Nominatim for it and the visa dialog may name the country outright - a human choosing "Nara, Japan" from a list that also offered Nara, Mali is exactly the certainty the confidence gate exists to look for. Typing without picking behaves as it always did |
| Airport picker | Flight items get From/To airport fields above the title, searching 3,271 IATA airports by city, airport name, code or alias. The table ships with the app (OurAirports, public domain, ~260 KB) rather than coming from an API: every airport API needs a secret key, which a static client-side app cannot hold, and a bundled file also works offline and is precached by the service worker. Aliases matter - Narita's municipality is "Narita", so without them a search for "tokyo" would never find NRT, and "new york" would never find EWR. Picking both writes the title as `City (CODE) to City (CODE)`, the same shape the day cards already parse for a travel day's departure city, so nothing new is stored on the item and a hand-written title is never overwritten. Editing an existing flight re-fills both fields from its title |
| Clear filters | A `✕ Clear filters` control sits in the toolbar whenever any filter or search term is active, and resets the search box, the type, status and traveler filters together. It is hidden when nothing is filtered. Previously the only way out of a filter combination was the link inside the "nothing matches" empty state, which never appeared while a filter still matched something |
| Read-only shared view | Opening a `share=` link renders someone else's itinerary and locks every action that would write to YOUR data. Only export trip (JSON / CSV / .ics), share, and the 12/24-hour toggle stay live in the trip menu; the other eight entries are visibly disabled rather than clickable-but-inert. "Backup all trips" is specifically among them, because in a shared view it produced a file named `trip-planner-backup.json` containing only the stranger's trip, which would have looked like total data loss on restore. The trip picker, the status pickers and the currency picker are disabled too, the cross-trip search is hidden entirely, and the `n` keyboard shortcut no longer opens the Add-item dialog |
| Read a booking PDF | `📄 Read a booking PDF` in the trip menu takes a flight or hotel confirmation - a PDF, or pasted text - and offers the items it found as ordinary proposal cards. Deterministic, not AI: airport codes resolve against the bundled table, and dates, times, booking reference and price are read by pattern. **The file is never uploaded and never stored**; it is read into memory, turned into text, and dropped, so nothing lands in the documents pocket. Every reading shows the LINE it came from and a confidence, because a wrong read has to be visible rather than merely plausible in a form field. Accepting one goes through the same validation, undo and save path as an assistant suggestion. Its one extra privilege is transcription provenance: a confirmation code and a `booked` status survive from a document (they were copied, not invented) where they are stripped from a model, and a transcribed price counts as real cost rather than an estimate. Dates are the delicate part: `08/12/2027` is read month-first by default, but a decisive date elsewhere on the page overrides that, and failing one, the reading that produces a possible trip wins - a confirmation whose dates imply a 31-day flight is being read the wrong way round. Whichever settled it is stated on screen. PDFs that are scans, or that store text as subset glyphs, are refused with a pointer to the paste box rather than guessed at |
| Route map | Numbered stops in visit order connected by a dashed route line (Leaflet + OSM, dark-mode tiles) |
| How to get there | Between consecutive stays in different places: distance (km/mi), compass heading, international-border flag, per-mode duration estimates, and pre-filled links to Google transit/driving, Google Flights and Rome2Rio |
| Import / export | JSON per trip, full backup of all trips, CSV export (includes per-item currency + converted columns, plus confirmation, travelers, bookBy and paymentMethod columns appended in that order so older spreadsheets keep their column order, the payment column carrying the picker's own wording rather than the stored token); import accepts trip files or full backups and re-normalizes traveler names against the trip roster. Attached documents are never included in exports |
| Calendar export | Export trip (.ics) in the trip menu: stays as all-day ranges, flights/transport as floating local-time events (overnight arrivals land on the right day), cancelled items excluded; imports into Google/Apple Calendar. A confirmation code rides along as a `Ref:` line in the event description, since the calendar entry is what a traveler opens at the gate, and a Book-by date and a payment method join it as `Book by:` (spelled out, not ISO) and `Payment:` lines whenever they are set |
| Installable PWA | manifest.webmanifest + sw.js (network-first: online loads always get the newest code; caches are an offline fallback only); timeline works offline after one visit, external APIs are never intercepted |
| Days view | Third view tab: one card per trip day with check-ins, check-outs, timed events, a "Nothing planned, staying at {hotel}" line on days covered only by a stay, and honest "No plans yet" days with no bed; today highlighted; print-friendly (printing in Days view outputs just the cards). Every row is the same shape - type tile, title and location, then price + Google Maps, then edit and delete - and the row asks its own CARD width (a container query, not the viewport) whether the price and Maps sit beside the title or wrap to their own line, so every card on a page wraps the same way. Cancelled rows carry a `Cancelled` badge and dim the two controls that are no longer actionable, keeping edit and delete at full strength |
| Budget | Optional per-trip budget in the trip dialog; summary chip shows confirmed-vs-budget and turns amber when exceeded. It never reads green over a total that silently excluded unconvertible money, and it reports a net refund honestly rather than painting green over a negative. The three summary chips that state a part-of-whole ratio in text (Progress, Nights booked, Budget) each carry a thin proportional bar under the value, reusing the same bar the Cost-by-type rows use, so the ratio reads at a glance instead of needing two figures and a division. The bar never introduces a number the chip's own text does not already state, never renders past 100% when spend exceeds budget, and renders at zero rather than negative on a refund; the chips carrying no ratio are untouched |
| Cost per traveler | Name two or more travelers (comma-separated, up to 6) in the trip dialog and each item's Booking section gains a "Who's this for" control. An item left as Everyone splits evenly across all travelers; pick some names to split it only among them. A "Cost per traveler" block under the totals bar shows each person's converted total, and a traveler owed an amount that could not be converted is flagged amber the same way the Confirmed total is, never silently under-counted. A trip that names no second traveler shows none of this and computes exactly as before |
| Uneven splits | Real shared costs are rarely even, so with two or more specific people picked on a costed item a "Split evenly / Split by amount" toggle takes exact per-person figures instead of an automatic divide. Switching to it prefills the even split and distributes the odd cent (a $100 item across three opens as 33.34/33.33/33.33), so the default always adds up. Amounts that do not sum to the item's cost, checked to the cent, block the save with "Split amounts must add up to {cost}" rather than storing a total that lies. Cost per traveler and Settle up both spend the real figures, so a $70/$30 item settles as $70/$30. Changing who the split is for keeps the numbers already typed and only fills one in for anyone newly added; dropping below two people discards them and reverts to an even split |
| Settle up | With two or more named travelers, each item's "Who's this for" section also asks who actually paid ("Paid by", defaulting to a blank "Not tracked"). A "Settle up" block under the per-traveler totals nets every Booked, convertible, payer-tagged cost down to the fewest possible payments and states them as "{debtor} owes {creditor} {amount}", so two people who each covered different bookings see one line, not two. Amounts are rounded to cents before pairing, so a stray sub-cent line can never appear. Nothing tagged yet reads "Add \"Paid by\" to a cost to see who owes whom" rather than a row of misleading zeroes, and everything squaring up reads "All settled up" in green with a ✅, visually distinct from that gray not-set-up-yet placeholder so the one piece of good news the card delivers does not read like a prompt to go do something. A payer is re-spelled or dropped when the roster is edited, so a name that left the trip never lingers |
| Cost by type | A "Cost by type" block under the totals bar breaks the trip's Booked, costed items down per type (Flight, Stay, Transport, Local travel, Activity, Note), biggest first, in the display currency. A type with nothing booked and costed gets no row at all rather than a $0.00 placeholder, and a row holding money that could not be converted is flagged amber with "+ N not converted", the same honesty rule the Confirmed total follows. Each row carries a thin proportional bar sized against the largest row, so the line item eating the budget is obvious without comparing figures; an amber unconverted row keeps its normal bar color, leaving the honesty cue on the text alone. It is gated on cost data alone, so it shows on a solo trip too |
| Cash needed | Each item's Booking section takes an optional payment method (Not tracked, Cash, Card, Prepaid / already paid). Tag anything as Cash and a "Cash needed" block under the totals answers how much cash to carry per currency, in the currency actually entered and never converted, so a Japan-plus-Thailand trip reads its yen and its baht as separate lines. One row per currency, sorted by code, and a currency holding nothing gets no row rather than a $0.00 placeholder; a refund nets into its currency and is not hidden. Cancelling an item or untagging it drops the amount on the next render. It is gated on cash tags alone, so it shows on a solo trip too. This block and the Cost per traveler, Settle up and Cost by type blocks now read as one iconed group set apart from the totals bar, rather than a stack of identical cards |
| Filter by traveler | With two or more named travelers the toolbar gains a third filter next to type and status. Picking a name narrows Timeline and Days view to that person's agenda: their own items plus everything left as Everyone. It ANDs with the type, status and search filters, and it changes only which rows are drawn, never what is computed, so the night-coverage strip, the warnings panel and the totals bar all keep reading for the whole trip. Clearing filters resets it, and a name the next trip's roster lacks is dropped rather than silently hiding rows |
| Up next | A live chip at the front of the summary row answers "what now" mid-trip. Items carrying both a date and a real clock time qualify (a stay's assumed check-in time is not a fact, so stays never do); inside a flight, transport or local leg it reads `Now: {title}`, otherwise it counts down the soonest item within 36 hours as `Up next: {title} in 2h`. Past that window, or with nothing left to time, it does not render at all. It repaints itself every 30 seconds, and clicking it jumps to that row on the Timeline |
| Packing list | 🎒 Packing list in the trip menu keeps a per-trip checklist with a "{checked} of {total} packed" counter. It is seeded once, on first open, from what the trip actually contains: universal basics always, a boarding-pass row only when the trip has a flight, and a warm-layer row only when a leg runs overnight. After that it is yours: it is never reseeded, adds and deletes and checks are each one undo step, and a list you empty completely stays empty instead of springing back. It rides along with the trip through save and sync, and is deliberately kept out of share links |
| Confirmation numbers | Each item has an optional confirmation / reference field (up to 40 characters). When set it shows a `Ref:` tag on the timeline row and the Days-view check-in card (not on a stay's checkout row), search matches it alongside title, place and details, and it rides along in CSV export, the calendar (.ics) description and share links. The AI assistant is deliberately blocked from writing it, since a booking code is a fact only the traveler holds |
| Example trips | An empty plan offers a dozen ready-made trips (7 to 14 days, varying densities), listed A to Z; a trip name that matches a destination preselects it; the loader routes to the base app URL, not a stale hash |
| Deep-linkable views | `#timeline`, `#days` and `#map` boot straight into that view and survive a refresh; a share fragment is never overwritten |
| Route options | Opening a leg shows distance, per-mode duration, cost and CO2 estimates, badges, curated corridor facts and operator links, with a match-confidence note under each end and an explicit estimates-not-quotes caveat |
| Multi-currency costs | Each item's cost can be entered in its own currency and converts into the trip's display currency using daily rates (api.frankfurter.dev, cached 24h); switching the display currency converts, never relabels; failed rate fetches show a note + Retry instead of fake 1:1 rates |
| Share link | Share itinerary produces a URL with the whole trip compressed into the fragment (no server, payload slimmed of empty fields, including confirmation codes, Book-by dates, payment tags, and the traveler roster and per-item split); opens read-only with a banner and "Import as my trip", re-normalizing traveler names on import. Links over ~8k chars copy with a truncation warning; a 30k hard cap points to JSON export |
| Continuity warnings | Consecutive stays in different (geocoded) cities with no flight/transport between them raise a warning naming both cities |
| Typical weather | Day cards show a typical temperature range for {place} that month, averaged over the last 5 years of Open-Meteo history (cached per place+month), with a visible caveat that it is historical climate, not a forecast |
| Visa reminders | Visa rows marked e-Visa/visa required offer "Add reminder", creating an "Apply for {country} visa" to-book item dated 30 days before the trip |
| Documents pocket | Attach images/PDFs (booking confirmations, QR codes) to saved items; stored on-device in IndexedDB (2MB/file, 10/item), paperclip indicators, purged with the item, excluded from exports and sync |
| Trip-in-progress | During the trip the countdown chip becomes "Day X of Y", past rows dim, and the page opens scrolled to today; afterwards it reads "Trip completed" |
| Visa requirements | 🛂 Visas: your passport is auto-guessed from the departure flight (and overridable, saved), and every country on the itinerary shows its requirement (visa-free with days, visa on arrival, e-Visa/eTA, visa required), derived from the maintained Passport Index dataset whose publication date is shown on the dialog (not implied to be live). A country is only named when its place geocodes confidently; an ambiguous match is said out loud as "country not confirmed" rather than guessed, so the dialog never states a requirement for the wrong country. That warning is suppressed in the one case where it could tell the traveller nothing: when the ambiguous place's best-guess country is already listed on the strength of a confident stop elsewhere on the trip (Masada on a trip already showing Israel via Tel Aviv and Jerusalem). The guess still never creates a row and is never attached to a country's place list, so a place guessing a country that is not otherwise on the trip warns exactly as before. Per-country Wikipedia verify links and an always-verify-officially caveat; countries can also be added manually (layovers, border crossings, road trips), stored per trip and removable. The same dialog takes an optional passport expiry date, since being turned away at the gate over passport validity has nothing to do with visas but lives in the same moment: an expiry on or before the trip's last day reads in red, one within 6 months of the return reads in amber with the honest caveat that each country sets its own rule and you should check it, and anything further out says nothing at all rather than a reassuring green tick. Like the passport country it belongs to the device rather than a trip, so it follows you between trips, and like the passport country it stays out of every JSON, CSV, calendar and share export: it is a personal fact, not trip data |
| Settings | 12/24-hour time format (saved and synced); the trip menu's actions are grouped under Trip, Import & export and Preferences captions, with Delete trip standing on its own at the bottom; the entry that opens the trip dialog reads "Trip settings" rather than naming two of the four things it edits (it takes the name, currency, budget AND traveller roster), and removing a traveller now says how many items lose their who-paid assignment before it happens; Escape closes one layer at a time, topmost first (an open dialog, then the assistant panel, then the search panel, then the trip menu), so a popover can no longer be left stranded open underneath a dialog, and closing either header popover by any route returns keyboard focus to the button that opened it (the two deliberate exceptions being a search result, which hands off to the jumped-to row, and a menu action that opens a dialog, which hands off into that dialog); a small "build N" tag at the bottom of the trip menu identifies the loaded code version (staleness diagnostics for the PWA cache) |
| Cloud sync | Optional: sign in via the site header and trips/preferences sync across devices via Firestore (`sync-system/`), same as the other apps |
| AI assistant | 🤖 A picker builds the request (slot types and counts, style, wake/return times, repeats, budget, free text) instead of the traveller typing prose, and the same request feeds all three tiers. Replies come back as separate timed items rather than one blob, with alternatives per slot the traveller picks between before anything is added. Edits arrive as accept/reject proposal cards (never auto-applied, never marked Booked or Cancelled, an update never un-books a real reservation, and every accept flows through undo). Three tiers chosen from a privacy-labelled picker: (1) copy/paste a ready-made package into any AI and paste its reply back, no key and nothing sent; (2) bring your own OpenAI or Gemini key, stored only in this browser, calling the provider directly; (3) the site's free shared assistant (Google Gemini, rate-limited per day). The assistant refuses to state visa, passport, vaccination or customs rules and points at the destination government instead. Replies render Markdown; chat history is kept per trip in `localStorage` (capped at 40 messages) and can be cleared; suggestions always include a Google Maps verify link and, when an owner Places key is configured, a Google star rating |

## Site assistant setup (owner)

Tier 3 (the free shared assistant) is served by the Netlify function
`netlify/functions/tp-assist.mjs`, which proxies Google Gemini behind per-client
and global daily rate limits. Env vars are not injected into functions on this
site, so the shared key lives in a Blob, written once out-of-band:

```
# 1. Get a free Gemini API key at https://aistudio.google.com/apikey
# 2. Point the CLI at the project that serves shevato.com (blob stores are
#    per-project, so writing this while linked elsewhere silently does nothing):
netlify status
# 3. Store it (the key never travels over HTTP; it is set via the CLI):
netlify blobs:set trip-planner-assist config '{"geminiKey":"<key>"}'
# Disable the shared assistant again:
netlify blobs:set trip-planner-assist config '{}'
```

With no key set the endpoint returns `503 not_configured` and the UI tells the
traveller to use Tier 1 or bring their own key. Tiers 1 and 2 need no setup.

Two failure modes look alike from the browser but are not: `503 not_configured`
means the key is missing from *this* project's store, while `502 upstream` means
the key was found and Gemini itself rejected the call (most often a retired
`GEMINI_MODEL` pin, see the note in `tp-assist.mjs`). A `429` means a quota was
hit, either this function's own daily limits or Google's. The function logs the
upstream status and body; the key is never logged.

**Google's free tier is the real ceiling, not our limiter.** Measured
2026-07-19 on a free key: `gemini-3.5-flash` allows 5 requests/minute and
250K tokens/minute, and the API refuses further calls once a
`generate_content_free_tier_requests` allowance of about 20 (apparently daily)
is spent. This function's own caps (10/client/hour, 30/client/day, 400/day
global, in `lib/tp-assist-quota.mjs`) are far above that, so on the free tier
travellers hit Google's wall first and see "at capacity". Check the real numbers
at https://aistudio.google.com/rate-limit; enabling billing on the Google Cloud
project raises the limits and costs fractions of a cent per turn.

```
├── tp-assist.mjs             # Rate-limited Gemini proxy (origin guard, quota, no key leak,
│                             #   oversized-trip trimming, shared prompt imported from trip-logic)
├── lib/tp-assist-store.mjs   # Blob store handles (config + usage)
├── lib/tp-assist-quota.mjs   # Pure per-client / global daily quota math
├── tp-places.mjs             # Google Places ratings proxy (two-call strategy, owner-token tier)
├── lib/tp-places-lookup.mjs  # Resolve query -> place ID -> rating; place-ID cache 30d, ratings never cached
├── lib/tp-places-match.mjs   # No-match classification before anything is billed
├── lib/tp-places-quota.mjs   # Compare-and-swap quota (public + separate owner buckets)
├── lib/tp-places-store.mjs   # Blob store handles (config + usage)
├── lib/tp-places-usage.mjs   # CAS usage accounting
└── tests/                    # node:test for the quota math, matching, and handler guards
```

The Places ratings proxy is dormant until an owner writes a `placesKey` (and,
optionally, an `ownerToken` for a higher personal rate tier) into the
`trip-planner-places` Blob, the same out-of-band way the assistant key is set
above. Place IDs are cached 30 days; names and ratings are never cached, because
no Google caching exception covers those fields.

## Tests

```
npm run test:trip-planner
```

Pure-logic tests via `node --test` against `js/trip-logic.js` (dual-exposed as `window.TripLogic` and a CommonJS module). No installs, no config.

The Tier 3 function's quota math and request guards have their own suite (run by the root `npm test`, or on their own with `npm run test:tp-assist-quota`).
